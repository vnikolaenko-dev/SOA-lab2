01 / Роли

Кто кого вызывает

Collection — вызываемый

collection-service владеет коллекцией десантников: создаёт, обновляет, удаляет, фильтрует и возвращает SpaceMarine. Данные находятся в схеме PostgreSQL collection.

Starship — вызывающий

starship-service управляет посадкой, высадкой и экипажем. Для проверки десантника и получения его данных вызывает Collection через Zuul. Собственные записи посадки хранит в схеме starship.

Это роли в конкретном межсервисном взаимодействии. При внешнем запросе клиент вызывает Starship, а Starship внутри обработки становится клиентом Collection. Zuul проксирует оба обращения.

Почему разные поколения Spring? Zuul starter основан на javax.servlet и используется на совместимом стеке Boot 2 / Hoxton. В Boot 3 применяются jakarta.servlet. В Starship подключена сама библиотека Netflix Ribbon с собственным адаптером к RestClient, без старого Spring Cloud Ribbon starter.

04 / Четыре компонента Spring Cloud
Настройки, адреса, выбор и проксирование


Config Server
Отвечает на вопрос: «С какими настройками запуститься?» Сервер читает общие свойства из application.properties, а свойства конкретного приложения — из файла с его именем. В проекте включён профиль native; Git-репозиторий не нужен.
Клиент с именем starship-service запрашивает конфигурацию /starship-service/default. Ответ содержит propertySources. Из них Spring собирает Environment, разрешает ${...} и внедряет значения через @Value и автоконфигурацию.
spring.application.name=starship-service
spring.config.import=configserver:${CONFIG_SERVER_URL:http://localhost:8888}

# В удалённом starship-service.properties:
collection.base-url=http://api-gateway/api/collection-service
Boot 3 использует spring.config.import. Старый gateway использует раннюю загрузку из bootstrap.properties и spring.cloud.config.uri. Импорт обязателен; для gateway включён fail-fast. Изменение файла в Config Server не означает автоматического обновления уже созданных bean: в текущем проекте изменения применяют перезапуском.
Classpath-конфигурация встроена в JAR Config Server. Чтобы изменить её в Docker, нужно пересобрать Config Server либо подключить внешний каталог через CONFIG_REPOSITORY.


Eureka
Отвечает на вопрос: «Какие экземпляры сервиса известны?» Сервис регистрирует имя, instance ID, IP/hostname, порт и статус. Несколько экземпляров с одним spring.application.name образуют одну логическую группу.
Клиенты отправляют heartbeat и получают копию реестра. Приложение читает её через DiscoveryClient.getInstances(serviceId), поэтому не выполняет отдельный сетевой поиск перед каждым бизнес-запросом.
eureka.client.service-url.defaultZone=${EUREKA_URL:http://localhost:8761/eureka/}
eureka.instance.prefer-ip-address=true
У сервера Eureka выключены регистрация самого себя и получение реестра от соседей. По умолчанию heartbeat и fetch выполняются примерно раз в 30 секунд. Lease, серверный response cache, клиентский fetch и Ribbon server list создают задержки видимости. Self-preservation может задерживать удаление исчезнувших экземпляров.
Eureka не пересылает бизнес-запросы. Она передаёт информацию об адресах; после выбора экземпляра HTTP отправляет клиент или gateway.


Netflix Ribbon
Отвечает на вопрос: «Какой экземпляр выбрать сейчас?» Это клиентская библиотека в JVM, а не самостоятельный сетевой сервер. В проекте используется правило RoundRobinRule: обращения чередуются между доступными экземплярами.
В Starship один BaseLoadBalancer живёт всё время работы Spring-контекста. Перед запросом адаптер обновляет список из DiscoveryClient и вызывает chooseServer(null). Список и выбор защищены блокировкой; сам HTTP выполняется вне неё.
var servers = discovery.getInstances(serviceId).stream()
    .map(i -> new Server(i.isSecure() ? "https" : "http",
                         i.getHost(), i.getPort()))
    .distinct().toList();
loadBalancer.setServersList(servers);
Server selected = loadBalancer.chooseServer(null);
Starship выбирает экземпляр api-gateway. Внутри Zuul другой Ribbon выбирает экземпляр collection-service или starship-service. Их счётчики независимы. Первый выбранный экземпляр не гарантирован. Наличие адреса в реестре не гарантирует, что процесс ещё жив.


Zuul Proxy
Отвечает на вопрос: «Куда и как переслать этот HTTP-запрос?» @EnableZuulProxy включает маршруты и цепочку фильтров: pre → route → post; при ошибках используются error-фильтры.
  1. PreDecorationFilter сопоставляет путь маршруту и определяет service ID.
  2. ApiPathFilter добавляет внутренний префикс /api/v1 после удаления публичного префикса.
  3. RibbonRoutingFilter находит экземпляр через Ribbon и выполняет HTTP.
  4. ApiLocationFilter переводит Location из внутреннего API-пути в публичный.
  5. SendResponseFilter передаёт клиенту статус, заголовки и тело ответа.
zuul.routes.collection-api.path=/api/collection-service/**
zuul.routes.collection-api.service-id=collection-service
zuul.ignored-services=*
zuul.retryable=false
Явный список маршрутов не позволяет автоматически открыть все сервисы из Eureka. Используется изоляция Hystrix SEMAPHORE: обработка идёт в потоке запроса, с ограничением параллелизма. HTTP-тайм-ауты Ribbon остаются включены; автоматические повторы отключены, чтобы случайно не повторить изменение данных.


Для старого bootstrap-клиента gateway удалённые свойства имеют высокий приоритет. В удалённом api-gateway.properties заданы spring.cloud.config.allow-override=true и spring.cloud.config.override-system-properties=false, чтобы CLI и environment могли переопределять удалённые значения, например server.port. Для Boot 3 используется механизм Config Data.
Как переписывается путь
ВходПосле stripPrefixРеальный upstream

06 / Интерактивная модель Eureka
Почему после сбоя адрес ещё виден
Остановите процесс Collection A и переключайте стадии. Модель намеренно разделяет реальные процессы, серверный реестр и локальную копию клиента. Она не рассчитывает точное время lease и не моделирует self-preservation.
Реальные процессы

        07 / Технологии приложения
        Что делает каждый слой
        

        Java и Maven
        21 / 11
        Java-код компилируется в bytecode и выполняется JVM. Maven описывает модули, зависимости и плагины в POM. Корневой POM агрегирует проекты; каждый модуль наследует собственный Spring Boot parent.
        Жизненный цикл сборки и пример
        generate-sources создаёт Java из OpenAPI; compile компилирует; test запускает тесты; package создаёт WAR/JAR; verify выполняет проверки жизненного цикла. Boot repackage добавляет launcher и зависимости для запуска через java -jar.
        .\mvnw.cmd verify
.\mvnw.cmd -pl api-gateway,starship-service verify
java -jar api-gateway/target/api-gateway-1.0.0.jar
        Maven Wrapper фиксирует способ запуска Maven без ручной установки. Gateway компилируется для Java 11, поэтому его Docker runtime — JRE 11. Остальные сервисы требуют Java 21. При сборке всего проекта нужен JDK 21.
        

        Spring Boot и DI
        3.5 / 2.3
        Spring создаёт компоненты приложения, связывает зависимости через конструкторы и управляет их жизненным циклом. Boot включает подходящие автоконфигурации по библиотекам на classpath и свойствам.
        Bean, конфигурация и запуск
        @Configuration
class ClientConfiguration {
    @Bean(destroyMethod = "shutdown")
    BaseLoadBalancer loadBalancer() {
        return new BaseLoadBalancer();
    }
}
        @SpringBootApplication объединяет конфигурацию, component scan и автоконфигурацию. @Service, @Component и @Repository отмечают прикладные классы. Конструктор с CollectionClient позволяет Spring внедрить готовый клиент. destroyMethod освобождает ресурсы Ribbon при закрытии контекста.
        

        Spring MVC и REST
        Servlet / HTTP
        Встроенный Tomcat принимает соединение. DispatcherServlet находит обработчик, конвертер Jackson читает JSON в DTO, Bean Validation проверяет вход, а delegate вызывает бизнес-сервис.
        Методы и цепочка обработки
        HTTP → Tomcat → DispatcherServlet
→ generated Controller → handwritten Delegate
→ CommandService / QueryService → Repository
→ DTO → Jackson → HTTP response
        GET читает данные; POST создаёт ресурс или выполняет команду; PUT заменяет; PATCH меняет указанные поля; DELETE удаляет. Query-параметры управляют пагинацией, фильтром и сортировкой. HTTP-статус передаёт результат: 201 — создано, 204 — успешно без тела, 400 — неверный ввод, 404 — нет ресурса, 409 — конфликт.
        REST — стиль взаимодействия через ресурсы и HTTP. Между запросами не хранится пользовательский HTTP-сеанс; состояние предметной области хранится в PostgreSQL.
        

        OpenAPI и генерация
        OpenAPI 3.0.3
        YAML-контракт описывает пути, параметры, JSON-схемы и ответы. Плагин OpenAPI Generator 7.12.0 во время сборки создаёт интерфейсы, DTO и контроллеры с delegate pattern. Ручная логика отделена от генерируемого кода.
        Контракт и публичные адреса
        servers:
  - url: /api/collection-service/
paths:
  /space-marines/{id}:
    get:
      operationId: getSpaceMarineById
      # parameters, responses, schemas...
        Публичный server URL ведёт через gateway. Внутренняя аннотация RequestMapping использует свойство openapi.spaceMarineCollection.base-path=/api/v1 из Config Server. Так публичный контракт и внутренний путь могут отличаться.
        Swagger UI — интерфейс в браузере, который читает контракт и позволяет выполнять запросы. Он не является самим API. Статический контракт доступен по /{service}/openapi.yaml. Forwarded headers помогают UI корректно учитывать префикс gateway.
        

        DTO, mapper и валидация
        Слои модели
        DTO описывает внешний JSON, JPA entity — структуру хранения, mapper преобразует представления. Bean Validation проверяет ограничения контракта до входа в бизнес-логику.
        Почему нужны разные модели
        DTO не должен случайно раскрывать все поля entity. Mapper явно определяет преобразование enum, вложенных объектов и patch-полей. Для PATCH важно различать отсутствующее поле и явно переданный null: в проекте исходные имена полей сохраняет PatchBodyFields.
        // Lombok генерирует builder и методы копирования:
SpaceMarine updated = existing.toBuilder()
    .withHealth(80)
    .build();
// Изменённую копию нужно сохранить в repository.
        Lombok генерирует код на этапе компиляции: getter, builder, with, конструкторы. @Builder(toBuilder=true, setterPrefix="with") позволяет копировать модель; @With возвращает копию с изменённым полем. Это не автоматическое сохранение в базе.
        

        CQRS в сервисном слое
        Разделение операций
        CommandService изменяет данные, QueryService читает. Это упрощает границы ответственности. В проекте общая PostgreSQL и общие сущности: отдельного read store, event sourcing и шины событий нет.
        Транзакции команд и запросов
        @Service
@Transactional
class StarshipCommandService {
    // проверка десантника по HTTP + запись boarding
}

@Service
@Transactional(readOnly = true)
class StarshipQueryService {
    // чтение посадок и получение десантников
}
        Spring применяет транзакционное поведение через proxy. readOnly задаёт режим для чтения; это не отдельная база и не универсальный запрет любых записей. HTTP-вызов Collection не входит в локальную транзакцию PostgreSQL Starship.
        

        Spring Data JPA / Hibernate
        ORM
        JPA описывает связь Java-объектов и таблиц. Hibernate реализует JPA, формирует SQL и отслеживает состояние сущностей. Spring Data создаёт реализации repository-интерфейсов.
        Как объект становится строкой
        @Entity
@Table(name = "space_marine")
class SpaceMarine {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
}
        @Embedded объединяет поля value object с основной таблицей; enum хранится строкой. Specifications строят критерии фильтрации Collection. Pageable задаёт страницу и сортировку. ddl-auto=validate проверяет соответствие схемы entity, но не создаёт таблицы.
        spring.jpa.open-in-view=false закрывает persistence context в границах сервисного слоя, а не держит его до окончания сериализации ответа. Модель не должна рассчитывать на ленивое чтение из базы во время формирования JSON вне транзакции.
        

        PostgreSQL, JDBC и Hikari
        PostgreSQL 16
        Один сервер PostgreSQL содержит базу space_marine и схемы collection, starship. JDBC-драйвер передаёт SQL по протоколу PostgreSQL; HikariCP переиспользует соединения.
        Изоляция данных и ограничения
        spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/space_marine}
spring.datasource.username=${DB_USER:root}
spring.datasource.password=${DB_PASSWORD}
spring.jpa.properties.hibernate.default_schema=starship
spring.datasource.hikari.connection-init-sql=SET search_path TO starship
        Разные схемы отделяют таблицы и миграции; это не физически разные базы. В boarding хранится marine_id без межсервисного внешнего ключа. Уникальное ограничение на marine_id запрещает двойную посадку; CHECK-ограничения защищают положительные ID и другие инварианты.
        Пул уменьшает стоимость открытия TCP/DB-соединений. Длительный HTTP-вызов внутри транзакции может дольше удерживать ресурсы; при росте нагрузки это нужно учитывать.
        

        Flyway
        Версии схемы
        При запуске приложения Flyway применяет ещё не выполненные SQL-миграции. Таблица истории хранит версии и контрольные суммы. Имена вида V1__boarding.sql задают порядок.
        Миграции и проверка ORM
        spring.flyway.schemas=starship
spring.flyway.default-schema=starship
spring.jpa.hibernate.ddl-auto=validate

CREATE TABLE boarding (
    id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    marine_id BIGINT CHECK (marine_id > 0),
    starship_id BIGINT NOT NULL CHECK (starship_id > 0)
);
        Flyway сначала создаёт/обновляет структуру, Hibernate затем сверяет её с entity. При несовпадении checksum уже применённого файла запуск может завершиться ошибкой. Развитие схемы оформляют новой миграцией, а не переписыванием V1 в существующей базе.
        

        RestClient и HTTP transport
        Spring / JDK
        RestClient — синхронный HTTP-клиент Starship. Он строит запросы и читает JSON в DTO. Перехватчик Ribbon разрешает логическое имя gateway до фактической отправки.
        От API клиента к TCP
        SpaceMarineDTO dto = client.get()
    .uri("/space-marines/{id}", id)
    .retrieve()
    .body(SpaceMarineDTO.class);
        JdkClientHttpRequestFactory использует HttpClient Java. В проекте connect timeout — 3 секунды, read timeout — 5 секунд. builder.clone() позволяет задать base URL без изменения исходного bean. Ошибки HTTP upstream и транспортные исключения различаются в CollectionClient.
        Retry не включён. Если сеть оборвалась после записи данных, повтор POST может вызвать повторное действие. Для безопасных повторов нужна отдельная стратегия идемпотентности, которой в текущем проекте нет.
        

        Caddy
        2
        Принимает внешний трафик на порту 80. API и пути ресурсов отправляет в Zuul; остальные пути — в frontend на host.docker.internal:3000. Сам Caddy не использует реестр Eureka.
        Чем Caddy отличается от Zuul
        :80 {
    handle /api/* {
        reverse_proxy api-gateway:8080
    }
    # /collection-service/* и /starship-service/* тоже в Zuul
    handle {
        reverse_proxy host.docker.internal:3000
    }
}
        Caddy знает Docker DNS-имя gateway. Zuul знает service ID бизнес-сервисов и получает адреса через discovery. Поэтому внешний reverse proxy и API Gateway — два разных уровня. При запросе непосредственно на :8080 Caddy пропускается, но Zuul остаётся.
        

        Docker и Compose
        Развёртывание
        Dockerfile собирает артефакт в Maven-образе и копирует его в меньший JRE-образ. Compose создаёт контейнеры, общую сеть, зависимости и постоянный volume PostgreSQL.
        Сеть, порты и готовность
        collection-service:
  expose:
    - "8081"        # не публикует порт на хост
api-gateway:
  ports:
    - "8080:8080"   # внешний вход
db:
  volumes:
    - postgres_data:/var/lib/postgresql/data
        В Docker localhost означает текущий контейнер, а не соседний сервис. Имена config-server, eureka-server и api-gateway разрешаются в Compose-сети. depends_on: service_started задаёт порядок запуска, но не гарантирует готовность HTTP. Для PostgreSQL используется healthcheck; discovery и загрузка реестров всё равно требуют времени.
        Пароль передаётся через DB_PASSWORD, а не должен попадать в HTML или Git. Volume сохраняет данные после перезапуска контейнера; временная БД сквозного теста создаётся без постоянного volume и удаляется после проверки.
        

        Hystrix внутри Zuul
        Legacy stack
        Стандартный RibbonRoutingFilter выполняет маршрутизируемый запрос через Hystrix command. Он добавляет изоляцию параллельных вызовов и учёт ошибок upstream. Это часть старого Spring Cloud Zuul, а не отдельный сервис проекта.
        Изоляция, circuit breaker и тайм-ауты
        При SEMAPHORE вызов остаётся в servlet-потоке, но ограничивается числом разрешённых одновременных исполнений. При THREAD использовался бы отдельный пул. Вложенный путь Starship → тот же gateway → Collection требует свободных servlet-потоков и лимитов; выбранная изоляция проверена отдельным HTTP-тестом вложенного вызова.
        zuul.ribbon-isolation-strategy=SEMAPHORE
hystrix.command.default.execution.timeout.enabled=false
ribbon.ConnectTimeout=3000
ribbon.ReadTimeout=15000
ribbon.MaxAutoRetries=0
ribbon.MaxAutoRetriesNextServer=0
        Отдельный execution timeout Hystrix выключен, но HTTP-тайм-ауты Ribbon продолжают ограничивать запрос. Circuit breaker может прекратить обращения к проблемному upstream после накопления ошибок и проверить его восстановление позднее. Наличие Hystrix не создаёт автоматическую компенсацию бизнес-операций; собственных fallback-ответов в проекте нет.

        09 / Границы данных
        Локальная транзакция и удалённый вызов
        Starship transactionВызвать Collection → проверить boarding → INSERT
        →
        HTTP через ZuulОтдельный запрос и отдельный сервис
        →
        Collection transactionSELECT space_marine в схеме collection
        @Transactional в Starship управляет его соединением с PostgreSQL. Она не делает HTTP-вызов распределённой транзакцией: между чтением десантника и записью посадки состояние Collection может измениться. В проекте нет 2PC, saga или событийной синхронизации.
        Что защищено базой
        Уникальность marine_id в boarding предотвращает две посадки одного десантника. CHECK-ограничения защищают допустимые значения. Сервисная проверка даёт понятную ошибку, а ограничение БД остаётся защитой при гонке.
        Что происходит при чтении экипажа
        Starship сначала читает список посадок, затем запрашивает каждого десантника через CollectionClient. Фильтрация экипажа и пагинация выполняются после получения данных. Это несколько сетевых обращений, а не один SQL JOIN между сервисами.

        10 / Запуск и диагностика
        Порядок важен, готовность — тоже
        1. PostgreSQL. База space_marine готова принимать соединения.
        2. Config Server. Отдаёт общие и сервисные свойства на :8888.
        3. Eureka. Загружает настройки и открывает реестр на :8761.
        4. Zuul. Получает конфигурацию, регистрируется как API-GATEWAY, создаёт маршруты.
        5. Collection и Starship. Получают настройки, выполняют Flyway, проверяют JPA-схему, открывают HTTP и регистрируются.
        6. Синхронизация discovery. В реестрах клиентов и списках Ribbon появляются нужные экземпляры. После этого доступны вложенные бизнес-вызовы.

        Если запрос не проходит
        1. Config Server отвечает на /starship-service/default, а collection.base-url указывает на api-gateway.
        2. В Eureka видны API-GATEWAY, COLLECTION-SERVICE и STARSHIP-SERVICE со статусом UP.
        3. Адреса из Eureka доступны из соответствующего клиента: Docker IP нельзя смешивать с изолированным локальным окружением.
        4. Дайте время на fetch реестра и обновление списка Ribbon. Регистрация в панели не означает мгновенную готовность каждого клиента.

        11 / Доказательства
        Что действительно проверено
        Автоматические тесты
        GatewayRoutingTest запускает настоящий встроенный Zuul и HTTP-upstream вместо бизнес-сервисов. Проверяет GET/POST/PATCH/DELETE, тело JSON, query и заголовки, 404/409, публичный Location, пути ресурсов, выбор двух экземпляров Collection и вложенный HTTP-вызов через тот же gateway.
        RibbonRequestInterceptorTest отдельно проверяет чередование адресов, сохранение encoded URI, обновление server list и отсутствие вызова старого сервера при пустом discovery.
        Сквозная проверка
        Скрипт запускает реальные Config Server, Eureka, Zuul, Collection, Starship и PostgreSQL на временных портах. Затем выполняет бизнес-операции через публичные маршруты gateway. Ниже встроен результат последнего завершённого запуска.
          Границы проверки. HTTP-тесты с upstream-моделями не доказывают работу БД или настоящей регистрации Eureka — для этого нужен сквозной запуск. Сквозной Java-запуск не проверяет сборку Docker-образов, frontend и внешний проход через Caddy. Подробности актуального запуска приведены в итоговом сообщении и отчёте. Нагрузочные, security- и отказоустойчивые испытания в эти проверки не входят.
