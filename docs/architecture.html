01 / Карта системы

Конфигурация и рабочие запросы

Config Server обслуживает загрузку настроек. После старта REST-запросы обрабатывают сами приложения: Config Server не участвует в каждом обращении к API.

Пунктир — передача конфигурации. Сплошные стрелки — обращения во время работы. Направление стрелок конфигурации показывает движение настроек; HTTP-запрос к Config Server инициирует клиент.

Caddy направляет /api/collection-service/* и /api/starship-service/* к соответствующим приложениям. Локально можно обращаться прямо на порты 8081 и 8082.

Сначала запускается config-server. Профиль native включает чтение файлов из classpath:/config-repository/. По умолчанию эти файлы упакованы в JAR сервера.

Локальный запуск

Импорт конфигурации обязателен. Сначала запустите Config Server, затем приложения. Если сервер недоступен при запуске, клиент завершится с ошибкой. Для работы также нужна доступная база данных.

Docker Compose

Импорт обязательный, включён fail-fast и до 20 попыток подключения. Compose ожидает запуска контейнера Config Server; готовности его HTTP API клиенты дожидаются повторными попытками. Для PostgreSQL настроена проверка здоровья.

Одинаковые имена application.properties здесь имеют разный смысл: внешний файл запускает сервер, вложенный файл сервер отдаёт клиентам.

Приоритет среди используемых в проекте источников: сверху выше
ИсточникПримерНазначение
Переменные окружения клиентаDB_URL, DB_PASSWORD, PORTЗначения для конкретного окружения. В текущих файлах используются через ${…}; прямое переопределение свойства тоже возможно, например SPRING_DATASOURCE_URL.
Файл сервиса на Config Serverstarship-service.propertiesНастройки отдельного приложения, при совпадении ключа перекрывают общие.
Общий файл на Config Serverconfig-repository/application.propertiesОдинаковые настройки для обоих клиентов.
Локальный файл клиентаsrc/main/resources/application.propertiesТолько имя приложения и обязательный импорт конфигурации. Рабочие настройки находятся на Config Server; тестовые — в src/test/resources.

Config Server отдаёт ссылку ${DB_PASSWORD}, а значение пароля берётся из окружения клиента. Передавайте его через DB_PASSWORD; значения по умолчанию нет. Изменение конфигурационного файла не обновляет уже запущенный сервис автоматически.

В текущем варианте файлы встроены в серверный JAR. После изменения исходных файлов пересоберите и перезапустите Config Server, затем клиентов. Для внешней папки можно задать CONFIG_REPOSITORY=file:/absolute/path/; в Docker её также нужно смонтировать.

JPA / Hibernate / PostgreSQL

В CQRS команды изменения данных обрабатывают CollectionCommandService и StarshipCommandService, чтение — соответствующие QueryService. Используется общая модель хранения; отдельной базы чтения и брокера сообщений нет.

Flyway выполняет и проверяет миграции БД при запуске, Hibernate проверяет структуру через ddl-auto=validate. Ошибка checksum у миграции блокирует запуск независимо от успешной загрузки настроек из Config Server.

05 / Практика

Запустить и проверить

Откройте три терминала в корне проекта. Сначала запустите сервер конфигурации, затем приложения с доступной PostgreSQL и корректными параметрами подключения.

# Терминал 1
.\mvnw.cmd -pl config-server spring-boot:run

# Терминал 2 (DB_USER и DB_URL задайте при необходимости)
$env:DB_PASSWORD = 'ваш-пароль'
.\mvnw.cmd -pl collection-service spring-boot:run

# Терминал 3
$env:DB_PASSWORD = 'ваш-пароль'
.\mvnw.cmd -pl starship-service spring-boot:run

Переменные окружения PowerShell действуют в том терминале, где заданы. Эти команды выполняются вами; страница сама не обращается к сервисам.

Посмотреть ответ Config Server

Настройки collection-service ↗
Настройки starship-service ↗

В JSON будут имя приложения, профиль и список propertySources. Это конфигурация, а не данные SpaceMarine.

Весь проект через Docker

$env:DB_PASSWORD = 'ваш-пароль'
docker compose up --build

В контейнерах клиенты используют http://config-server:8888, а БД — имя db. С хоста Config Server доступен на localhost:8888.
