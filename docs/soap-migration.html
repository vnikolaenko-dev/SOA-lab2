Второй, вызывающий сервис переведён на SOAP 1.1. Отдельный REST-адаптер сохраняет четыре операции, адреса и JSON-ответы существующего приложения.

Дальше из Starship: REST-вызовы collection-service:8081/api/v1 для получения десантников и PostgreSQL, схема starship, для записей о посадке. Первый сервис использует собственную схему collection.

Адаптер переносит параметры в вызов SOAP и возвращает полученный DTO. Он не фильтрует экипаж, не рассчитывает страницы, не проверяет существование десантников и не работает с базой. Проверка диапазонов и все решения о посадке остаются в SOAP-сервисе. Разбор HTTP-параметров и перевод ошибок относятся к преобразованию протокола.

В Docker между адаптером и двумя экземплярами SOAP-сервиса остаётся HAProxy. Его health check теперь обращается к WSDL, поскольку старого REST-адреса у SOAP-сервиса больше нет.

Что изменено в проекте

01 / КОНТРАКТ

starship-contract

Общий JAR: интерфейс StarshipSoapPort, JAXB DTO и StarshipFault. Одинаковые типы используются сервером и SOAP-клиентом.

02 / СЕРВИС

starship-service

REST-контроллеры и генерация REST API удалены. StarshipSoapEndpoint вызывает прежние command/query-сервисы. CXF публикует SOAP endpoint и WSDL.

03 / СОВМЕСТИМОСТЬ

starship-rest-adapter

Самостоятельное приложение без БД. StarshipRestController вызывает SOAP-прокси CXF. Gateway направляет прежние маршруты в адаптер.

В корневой Maven-сборке добавлены оба новых модуля и удалена ссылка на отсутствовавший api-gateway-2. Dockerfile собирают общий контракт перед зависимыми сервисами. Исходники фронтенда не менялись.

Один запрос на трёх уровнях

Нажмите на этап, чтобы увидеть, как посадка десантника превращается в SOAP-вызов и возвращается клиенту.

POST /api/starship-service/starship/42/load/7 HTTP/1.1
Host: localhost:18080
Accept: application/json

Gateway добавляет внутренний префикс /api/v1 и передаёт запрос адаптеру. Контроллер вызывает soap.loadSpaceMarine(42, 7).

POST /services/starships HTTP/1.1
Content-Type: text/xml; charset=utf-8

<s:Envelope xmlns:s="http://schemas.xmlsoap.org/soap/envelope/"
            xmlns:t="urn:soa:starship:v1">
  <s:Body>
    <t:loadSpaceMarine>
      <starshipId>42</starshipId>
      <spaceMarineId>7</spaceMarineId>
    </t:loadSpaceMarine>
  </s:Body>
</s:Envelope>

CXF выполняет сериализацию XML. На сервере метод endpoint проверяет ID и вызывает StarshipCommandService.load. Этот сервис получает десантника через первый REST-сервис и записывает посадку в БД.

Content-Type: application/json

{

Пример ответа. Адаптер десериализует SOAP в общий DTO, после чего Jackson формирует прежний JSON. Формат даты с секундами, nullable-поля и пустые массивы сохранены для существующих клиентских схем.

Зачем WSDL? Описание сервиса содержит четыре операции, типы XML, binding SOAP 1.1 и описание fault. Контракт создаётся CXF из JAX-WS интерфейса (code-first). DTO используют JAXB; даты и значения оружия представлены строками, их допустимость проверяет логика сервиса.

Публикация endpoint через EndpointImpl и путь CXF следуют официальной документации Apache CXF.

Ошибки без изменения клиентского контракта

При ошибке SOAP-сервис возвращает SOAP Fault с деталями status, message, field. Ответ SOAP Fault обычно имеет транспортный HTTP-статус 500. Адаптер берёт прикладной статус из detail и возвращает соответствующий REST-ответ.

SOAP Fault detail:
{
  status: 409,
  message: "Десантник уже на корабле",
  field: null
}
HTTP/1.1 409 Conflict
Content-Type: application/json

{"status":409,
 "message":"Десантник уже на корабле",
 "field":null}
СитуацияОтвет RESTГде принято решение
Неверный ID, диапазон страницы, фильтр400SOAP-сервис
Десантник отсутствует404SOAP-сервис / первый сервис
Десантник уже находится на корабле409SOAP-сервис и ограничение уникальности БД
SOAP недоступен / транспортный сбой503Перевод транспортной ошибки в адаптере
Неописанный SOAP Fault502Перевод протокольной ошибки в адаптере
HTTP-параметр не является числом / неверный HTTP-метод400 / 405HTTP-слой Spring MVC

Пустой корабль по-прежнему возвращает content: [], повторная высадка — 0. Повторяющиеся параметры filter передаются целиком: запятые внутри значений не разбивают одно условие на несколько.

Как запустить и повторить проверку

Локальный режим использует HTTP и отдельную PostgreSQL в Docker на порту 55432. Нужны JDK 21, Docker и Node.js. Maven запускается через wrapper из репозитория.

# PowerShell, из корня проекта
# Первый запуск: установить зависимости неизменённого фронтенда
cd soa-front
npx --yes pnpm@10 install --frozen-lockfile
cd ..

# Чистая сборка с тестами + запуск всех Java-сервисов и фронтенда
.\scripts\start-local.ps1 -WithFrontend

# Проверить настоящую цепочку gateway → REST → SOAP → REST → PostgreSQL
node scripts/test-e2e.mjs

# Дополнительно проверить ответы по исходным Zod-схемам фронтенда (Node 22.6+)
node --experimental-strip-types scripts/test-e2e.mjs --client-schemas

# Остановить процессы проекта и локальную БД (данные сохраняются)
.\scripts\stop-local.ps1

Если проект уже собран, используйте -SkipBuild. Логи и PID-файлы находятся в .local-run/; результаты сквозной проверки — в .local-run/e2e-results.json. Эти файлы исключены из Git.

Основной compose.yaml сохраняет HTTPS и требует имеющиеся в конфигурации переменные паролей и сертификаты. Для нового адаптера добавлен каталог certs/starship-rest-adapter: сертификат должен содержать DNS-имя starship-rest-adapter. Локальная проверка HTTP не подтверждает работоспособность TLS-развёртывания.
